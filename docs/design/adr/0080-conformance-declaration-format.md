# 0080. Conformance declaration format

Status: accepted. Date: 2026-09-18.

## Context

[`../30-conformance.md`](../30-conformance.md#declaring-conformance) requires a port to publish
seven things: the suite revision it ran, every level marked reached or excluded, the conformance
surface
behind each exclusion, the strategy surfaces it exposes, its driver's output, the wall time and
peak resident size it observed at `scale`, and its deviations. The rule states what is published
and names no form for it.

A declaration in prose is a claim nobody checks. The claims it makes are claims the manifest can
contradict: `manifest.json` carries the level table with the requires relation, the strategy
surfaces, and the artefact counts per level, and `10-specification.md` states which requirements
carry an RFC 2119 keyword that a deviation is permitted against. A declaration that names a level
the suite does not have, reaches a level whose required level it excludes, or deviates from a
requirement carrying `MUST` is wrong in a way a script sees.

[`0079`](0079-repository-layout-for-multiple-ports.md) puts several ports in one repository, so
declarations stop being one paragraph in one README and become a set a reader compares. Comparing
them by eye across four languages is where a stale revision goes unnoticed.

[`0061`](0061-suite-revision-identifier.md) already made the revision a content digest, which is
what makes a declaration checkable at all: a reader computes the revision from a suite tree and
compares it with the one a port declared.

## Decision

A declaration is a JSON file at `conformance/declarations/<port>.json`, one per port, written by
hand and named by the port identifier of
[`../35-port-conventions.md`](../35-port-conventions.md#port-identifier), which states the member
set.

`conformance/generator/verify_declarations.py` checks every declaration against `manifest.json` and
`10-specification.md`, and `run.sh` runs it after `verify_withdrawals.py`. It fails on a claim the
suite or the specification contradicts:

- a level the manifest's `levels` table does not list, or a level of that table the declaration does
  not name;
- a reached level whose required levels, transitively, are not all reached;
- an excluded level naming no conformance surface, or a reached level naming one;
- a strategy surface the manifest does not list, or an empty surface list, which `CORE-110` refuses;
- a case or file count above the totals the manifest holds for the declared levels, or short of them
  where the port exposes every strategy surface;
- a failure count above zero;
- the `scale` figures absent from a declaration that reaches `scale`;
- a deviation naming a requirement the specification does not state, or one that carries no
  `SHOULD`, `SHOULD NOT`, or `MAY`;
- a declaration whose port has no directory under `ports/`, or a driver report the declaration names
  and the repository does not hold.

A declaration naming an earlier revision than the manifest holds is reported as lagging and does not
fail the run. Regenerating the suite is what makes a declaration lag, so a fatal check there would
fail the commit that caused it and leave the repair to the ports.

## Consequences

The state of every port is data. A reader answers which ports reach `failover`, and which declared
against the current revision, by reading a directory rather than four READMEs, and a table of ports
against levels is computed rather than maintained.

The check bounds what a declaration may claim and does not establish that the run happened. The
counts, the failure count, and the `scale` figures are what the port reports about itself, and a
port that declares a level it did not run passes this check. What contradicts such a declaration is
the port's own job output, which the declaration names, and a second reader running the driver.

A regeneration leaves every declaration lagging, and the lag is visible in the run output rather
than in a broken build. A port re-runs the suite and updates one field, and until it does, its
declaration names a revision a reader can still fetch, which is what
[`0061`](0061-suite-revision-identifier.md) makes possible.

The file is hand-written and sits under `conformance/`, where everything else but the generator and
the reference driver is generated. The generated tree is `topologies/`, `vectors/`, `properties/`,
and `scenarios/`, and `declarations/` joins the suite on the revision rather than being computed
from it.

## Alternatives

A paragraph in each port's README. Rejected because nothing checks it, because the seven things are
easy to publish six of, and because comparing ports means reading prose in four places.

A declaration emitted by the port's own driver. Rejected because a claim generated by the
implementation under test is the implementation's report of itself in a second format, because the
machine, the runtime, and every deviation are a maintainer's words rather than a driver's, and
because it would make the declaration a second cross-language contract that every port implements an
emitter for.

Declarations inside `manifest.json`. Rejected because the manifest is generated from the suite's
content, and a hand-written claim in it is a member `build_manifest.py` would have to preserve
across a rebuild.

One file listing every port. Rejected because a port's declaration changes when that port releases,
and a shared file makes every release a conflict in a file four ports write to.

A declaration under `ports/<port>/`. Rejected because the declaration's counterpart is the manifest
rather than the source: a check reads the suite, the specification, and every declaration together,
and the set a reader compares is one directory.
